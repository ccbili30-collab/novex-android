# Novex 标准工具层与文档解析实施计划

状态：检查点 0 与检查点 1 已实现；检查点 2 尚未接入产品运行时
适用分支：`next`（下一版）  
基线提交：`53ae0bc2f9c2ffb9f34917a4c0228096852b7b84`  

技术选型、官方来源与体积比较见 [`docs/research/novex-document-parsing-tool.md`](research/novex-document-parsing-tool.md)。该研究列出了检查、目录、读取、搜索和资源获取五项原始能力；本实施计划为减少模型需要学习的工具数量，将目录合入检查、将搜索与资源定位合入读取，因此模型表面只保留两个深工具，底层能力没有减少。

## 一、这轮真正要解决的问题

Novex 不应继续把 Minis（原版框架）的 Shell（命令行外壳）、原始文件路径、数据库结构和内部枚举直接暴露给 AI（人工智能）。但这不等于削弱 AI 的能力。最终目标是：

- AI 仍能读取和创建文件、管理创作成果、保存进度、记录记忆；
- AI 能编辑世界、角色、文游及其模块；
- AI 能注册文游快捷按钮、面板和状态；
- AI 能可靠读取 Word（文字处理文档）、PDF（便携式文档格式）等用户文档；
- 用户能一次导入大量、超长且格式不同的资料，由 AI 在资料工作区持续整理、通读和理解；
- 所有能力都通过稳定、自描述、可审计、可测试的 Novex 工具，而不是猜内部实现；
- Minis 可以暂时作为 Adapter（适配器）留在工具层背后，但不能再决定 Novex 的工具契约。

当前最紧迫的缺口是文档解析。现有解析器并非完全不可用，而是接口形态错误：它把结构化文档压成一段纯文本，随后最多把每个附件 48,000 个字符、单次合计 96,000 个字符直接注入消息；较长内容又要求模型通过 Minis 的 `file_read`（文件读取）访问原始路径。这会造成结构丢失、上下文浪费、工具依赖和错误难以恢复。

## 二、已验证的现状

### 2.1 文档解析

- `.docx`（新版 Word 文档）优先使用 Apache POI（Apache Office 文档解析库）的 XWPF（新版 Word 解析模块）；失败后使用 ZIP/XML（压缩包／可扩展标记语言）降级解析。
- 真实夹具已经覆盖 Microsoft Word（微软文字处理软件）、WPS（办公软件）、LibreOffice（自由办公套件）和 Google Docs（谷歌文档）导出的 `.docx`，现有定向测试通过。
- 当前能读到正文、标题、列表、表格文字、超链接、页眉页脚、脚注尾注、批注、文本框和可见修订中的多数文本。
- 输出只有一段 Markdown（标记文本）字符串，没有稳定的标题、段落、表格、图片和来源定位结构。
- 旧 `.doc`（旧版 Word 文档）被产品显式判定为不支持；当前 19 MB 的 POI 阴影 JAR（Java 归档）中虽然包含 HWPF（旧版 Word 解析模块），但官方说明其维护和完整性有限，只能用于迁移期兼容实验，不能直接承诺生产支持。
- 图片型文档只能提示需要 OCR（光学字符识别）或视觉模型，目前没有标准降级通道。

### 2.2 模型工具

- `AgentTools.makeAgentTools()`（代理工具创建器）默认同时暴露 Shell、文件读写、浏览器、记忆、内容管理和文游工具，缺少按会话能力收敛。
- `novex_propose_content_changes`（Novex 内容变更提议）要求模型猜 `module_type`（模块类型）；非法值会泄露压缩后的内部类名，且错误不返回合法选项。
- 原始工具结果没有统一错误码、风险等级、修改对象、可撤销性和下一步提示。

以上结论来自代码静态检查、现有测试和定向执行；不代表旧 `.doc`、扫描件或超长复杂文档已经通过验收。

## 三、固定的工具层结构

```text
模型／页面／将来的自动化
          ↓
Novex 工具目录与权限策略
          ↓
Novex 领域工具接口
          ↓
内容／文档／工作区／存档／记忆／文游模块
          ↓
数据库、媒体、Android、Minis 适配器
```

工具层必须是 Deep Module（深模块）：调用方只学习少量稳定工具，复杂的格式识别、缓存、权限、事务、媒体引用和旧运行时细节全部藏在实现内。

### 3.1 所有工具统一返回信封

```json
{
  "ok": true,
  "code": "document.ready",
  "summary": "已解析 42 个内容块",
  "data": {},
  "warnings": [],
  "next_actions": [],
  "affected_refs": [],
  "side_effect": "none"
}
```

约束：

- `code`（稳定错误码）不能包含内部类名或混淆后的枚举名；
- 参数非法时返回 `allowed_values`（允许值），不让 AI 盲猜；
- 所有对象使用稳定引用，不把数据库编号和设备绝对路径当作公共接口；
- 每次写入记录来源会话、消息、分支、工具调用和修改对象；
- 读取失败不得产生部分写入，写入失败必须说明是否已回滚。

### 3.2 风险分级

| 等级 | 例子 | 行为 |
| --- | --- | --- |
| 只读 | 查看文档目录、搜索世界模块 | 直接执行，记录审计 |
| 会话局部且可逆 | 更新本局血量、创建临时文件 | 执行并显示结果，随分支恢复 |
| 共享内容写入 | 修改世界、角色、文游 | 提议 → 用户确认 → 原子应用 |
| 外部副作用 | 上传、联网发布、操作其他应用 | 单独授权，不与普通内容编辑合并 |

原始 Shell（命令行外壳）默认不提供。确有计算需求时进入受限 Workspace（工作区）执行器，只能访问当前会话授权目录，不得读取应用数据库、凭据、其他会话和系统目录。

### 3.3 工具按场景装配

模型每轮不再看到全套工具：

- 有文档附件时：提供文档查看工具；
- 挂载了可管理世界、角色或文游时：提供内容检查、提议和应用工具；
- 文游启动时：提供选择、面板、快捷按钮、局部状态和存档工具；
- 用户允许创作文件时：提供工作区与创作成果工具；
- 浏览器、图片生成、外部系统能力仅在已配置且当前需要时提供。

工具是否可用由会话配置与用户授权决定，不能由模型自行扩大权限。

资料导入只建立资料集和只读来源，不自动挂载为背景设定，不自动成为世界、角色或文游，也不自动触发卡片创建工具。用户以后明确要求“把这些资料整理成世界卡”时，才从资料理解结果进入内容提议与确认流程。

资料读取分为两条入口：少量资料可以在当前回合直接理解；大量资料、需要多轮通读的资料或网络资料必须先建立学习预检，由用户确认后启动学习整理任务。不能仅凭“模型支持 200K（20 万词元）或 1M（100 万词元）上下文”就跳过预检。

## 四、标准文档模块

### 4.1 对模型只暴露两个读取工具

#### `document_inspect`（文档检查）

用途：确认格式、解析状态、标题目录、块数量、表格与图片数量、警告和可用定位方式。默认返回紧凑目录，不返回全文。

主要参数：

- `document_ref`（文档引用）；
- `include_outline`（是否包含目录，默认 true）；
- `max_depth`（最大目录层级）。

#### `document_read`（文档读取）

用途：使用一种定位方式读取有限内容。支持：

- 按 `block_ids`（内容块编号）；
- 按 `heading_path`（标题路径）；
- 按 `query`（关键词搜索）；
- 按 `page_range`（页码范围，仅格式能够可靠提供时）；
- 按 `cursor`（游标）继续读取。

每次返回都带来源定位、下一页游标和是否截断。服务端设置硬上限，模型不能请求“一次返回整本书”。搜索属于读取工具的定位能力，不再增加一个几乎重复的浅工具。图片和嵌入资源也通过 `document_read` 的资源定位方式取得受控引用，不把二进制编码进普通文本结果。

文档导入由应用在用户选择文件后自动执行，不要求模型调用“解析”。写出 Word 或 PDF 属于创作成果导出，不和只读解析混为一个工具。

### 4.2 统一文档快照

原文件保持不变；解析后生成按 SHA-256（256 位安全散列算法）寻址的派生快照：

```text
DocumentSnapshot
├─ 文件身份、格式、校验值、解析器版本
├─ 标题与元数据
├─ 有序 DocumentBlock（文档内容块）
│  ├─ heading（标题）
│  ├─ paragraph（段落）
│  ├─ list_item（列表项）
│  ├─ table（表格）
│  ├─ image（图片）
│  ├─ note（脚注／尾注／批注）
│  └─ page_break（分页）
├─ MediaRef（媒体引用）
└─ 解析警告与来源定位
```

每个内容块有稳定编号、顺序、父标题、可搜索文本和源位置。文档再次上传且校验值相同时直接复用快照；解析器版本变化时才重建。

### 4.3 `.docx` 的落地顺序

1. 先让现有 POI 解析器输出统一文档快照，而不是大字符串；现有真实夹具继续作为行为基线。
2. 新增基于 Android `XmlPullParser`（XML 拉取解析器）和 ZIP 流的 OOXML（Office 开放 XML 格式）解析器，按正文顺序读取段落、表格、关系、样式、编号、页眉页脚、脚注尾注、批注与媒体引用。
3. 新解析器先作为默认快速路径，POI 作为兼容降级路径；两者通过同一接口和夹具比较。
4. 当结构、文本和错误处理达到约定一致后，移除 `.docx` 对 19 MB POI 阴影 JAR 的依赖；是否保留一份更小的 HWPF 旧 `.doc` 兼容包，依据真实旧文档夹具与构建体积再决定。

采用流式解析的原因是 `.docx` 本身是由多个 XML 部件和关系组成的压缩包；不必把完整 DOM（文档对象模型）或整份文档一次载入内存。Android 官方也把 `XmlPullParser` 推荐为高效、易维护的 XML 解析方式。

### 4.4 旧 `.doc`、PDF 和扫描件

- 旧 `.doc`：第一阶段只对当前归档中已有的 HWPF 做 Android（安卓系统）兼容与真实夹具实验；通过后可以在 POI 仍存在的迁移期提供低保真读取。长期默认是提示用户另存为 `.docx`，或由 Windows（视窗系统）／服务器的 LibreOffice 外部适配器转换。除非真实使用数据证明离线旧 `.doc` 是刚需，否则不为它保留重依赖。不能从零手写二进制 Word 格式。
- PDF：继续用 PDFBox Android（安卓 PDF 解析库），但输出统一内容块和页码定位；不把视觉排版误报为可靠阅读顺序。
- 扫描 PDF 或图片型 Word：返回 `ocr_required`（需要光学字符识别）状态，保留页图引用；OCR 在独立检查点接入，不能用空文本冒充成功。
- `.docm`（带宏 Word 文档）：可读取静态文档部件，但永不执行宏。

### 4.5 安全与资源限制

- 限制压缩包条目数、单项和总解压字节、嵌套深度、图片像素与解析时长；
- 禁用 XML 外部实体和文档类型声明；
- 所有解析在后台执行，可取消，不阻塞界面主线程；
- 原文件只读，派生媒体进入受引用保护的创作成果存储；
- 超限、加密、损坏和不支持格式都返回稳定状态，不闪退、不无限加载；
- 文档中的文字永远视为用户资料，不得被当成工具指令执行。

### 4.6 大批量资料整理与完整通读

单文档按需读取还不足以覆盖“用户一次丢入大量文件，让 AI 自己整理干净”的场景。Novex 需要把一批来源建成 `SourceCollection`（资料集），并把完整通读作为可恢复任务，而不是一次模型请求。

处理流程固定为：

```text
批量导入
  ↓
文件清单、格式识别、校验与去重
  ↓
每个文件建立目录和内容块索引
  ↓
AI 制定通读顺序并逐块读取
  ↓
文件级笔记、实体、时间、观点和疑点
  ↓
跨文件分类、版本关系、冲突和综合理解
  ↓
用户确认整理结果
```

这里必须区分两种读取：

- **检索读取**：围绕当前问题找到相关片段，速度快但不能证明理解了全部资料；
- **完整通读**：覆盖每个可读内容块，适合首次资料整理、长篇设定研究和深度共创准备。

应用自动维护 `ReviewLedger`（通读账本），而不是要求 AI 自己声称“我看完了”：

- 每个文件状态为未开始、进行中、已通读、重复、失败或需 OCR；
- 记录已读取的内容块、总内容块、最后游标和解析警告；
- `document_read` 每次成功返回后自动增加覆盖范围，重复读取不重复计数；
- 应用重启、模型切换和对话压缩后可以继续未完成位置；
- 只有所有可读内容块均已覆盖，或者明确列出无法读取的文件，才能报告“通读完成”。

为了让 AI 在有限上下文中理解超长资料，使用分层工作笔记：

1. 内容块笔记保留原文锚点；
2. 章节笔记由内容块笔记归纳；
3. 文件笔记由章节笔记归纳；
4. 资料集总览由文件笔记归纳；
5. 后续追问可以沿锚点回读原文，不把摘要当作唯一事实来源。

“整理干净”至少包括：

- 以 SHA-256（256 位安全散列算法）识别完全重复文件；
- 识别标题近似、正文高度重叠的不同版本，但不静默合并；
- 按用户目标形成虚拟目录、标签和主题，不移动或改写原件；
- 抽取人物、地点、时间、术语和来源关系作为工作索引；
- 标记相互矛盾、缺少来源和无法确认的内容；
- 产生带来源锚点的整理报告、目录或研究笔记。

资料整理结果默认写入工作区笔记和草稿。除非用户明确下达转换命令，否则不得创建世界、角色、分身、文游或修改已有卡片。即使用户要求转换，也必须继续使用 `novex_propose_content_changes`（Novex 内容变更提议）和确认后原子应用，不能把整理笔记直接映射到数据库。

资料集的挂载、移除和工作笔记跟随当前对话分支；切换分支时恢复该路径实际拥有的资料范围。解析快照和精确重复缓存可以跨分支安全复用，因为它们只由原文件校验值决定；复用缓存不得重新执行 OCR、联网转换或其他外部副作用。

工具层不需要为批量资料增加一组重复工具：

- `workspace_inspect` 返回资料集清单、解析状态、重复关系与通读进度；
- `document_inspect` 接受单个文档或一批文档引用，返回紧凑目录；
- `document_read` 负责检索读取或按游标完整通读，并支持受总输出预算约束的小批量定位；
- `workspace_write` 和 `workspace_edit` 保存整理笔记、虚拟分类与综合结果；
- 覆盖率、去重、缓存和恢复由文档模块自动完成，不暴露为模型要手工维护的文件。

### 4.7 学习预检与用户确认

文件加入后，应用先使用本地信息判断走哪条路径：

```text
少量、可直接读取
  → 明确显示将直接加入当前理解范围
  → 当前回合读取并回答

大量、超长、需 OCR 或需联网
  → 学习预检
  → 用户确认
  → 可暂停、可恢复的学习整理任务
```

是否属于“少量”不能只看文件大小。决策至少考虑：文件数量、解析后的估算词元、当前对话已占用上下文、模型可用输入窗口、图片和扫描页、是否需要联网，以及用户设置的单次直接读取预算。初始阈值作为可调整产品参数并由五名长文用户压力测试校准，不写成不可变领域规则；模型窗口或费用未知时，一律走学习预检。

学习预检界面必须明确说明：

- 将处理多少文件、页面、图片和估算词元；
- 哪些文件能读取，哪些需要 OCR、密码或格式转换；
- 将执行本地解析、分批模型阅读、笔记生成、去重、分类和跨文件综合中的哪些步骤；
- 预计模型调用轮数、输入／输出 Token（词元）区间和可能费用；估算不是账单承诺；
- 可能耗费的时间、网络流量、电量和本地存储；
- 哪些原文会发送给当前模型提供商，以及联网来源会访问哪些站点；
- 结果是资料目录、通读进度、整理笔记和综合理解，不会自动创建卡；
- 可以暂停、取消或稍后继续；取消时保留已确认的解析缓存和工作笔记，并说明哪些内容尚未读完。

原生确认卡的最低信息结构为：

```text
准备整理 38 份资料

预计规模：约 640,000 Token（词元）原文
执行方式：本地解析 → 分批通读 → 去重分类 → 综合笔记
预计消耗：模型输入／输出为区间估算，实际用量持续显示
会发送：可读正文片段至当前模型提供商
不会执行：创建世界卡、角色卡、文游，修改原始文件
风险：可能产生较高模型费用并耗时；3 份扫描件需要 OCR

[开始整理] [调整范围] [取消]
```

数值只能来自真实预检，无法可靠估算时显示“未知并可能较高”，不能用伪精确数字诱导确认。

状态机固定为：

```text
本地扫描
├─ 可直接理解
└─ 等待确认
      ↓
   建立索引
      ↓
   分批通读
      ↓
   交叉整理
      ↓
   完成

任一执行状态 → 已暂停／已取消／部分失败
```

关键约束：

- 用户确认前不得启动付费模型调用、大规模下载、OCR 或格式转换；
- 确认绑定一次具体预检快照，新增文件、扩大 Wiki 抓取范围或切换更昂贵模型后必须重新预检；
- 估算显著超出确认范围时自动暂停并再次询问，不能无上限继续消耗；
- 学习任务的实际 Token、时间和来源读取量持续记账，用户随时可查看；
- 用户可以对少量资料手动选择“整理学习”，也可以把大任务缩小范围后重新预检。

学习整理工具保持较小表面：

- `learning_prepare`（学习准备）：生成只读预检与稳定任务计划，不开始付费学习；
- `workspace_inspect`（工作区检查）：查看进度、剩余范围、实际消耗和风险；
- `learning_start`（开始学习）是应用内部命令，只能由原生确认卡或应用验证过的真实用户确认触发，不作为普通模型工具暴露；
- 暂停、继续与取消优先由原生界面控制，也可通过受限且可审计的任务命令执行。

模型调用 `learning_prepare` 后必须停止并等待。确认规则与共享内容的“提议 → 用户确认 → 应用”一致，模型不能伪造确认文本，也不能在生成预检的同一回合启动任务。

### 4.8 Wiki 与网络资料接入

Wiki（维基）不是另一套学习系统，而是一种 `SourceConnector`（资料来源适配器）。第一阶段接入 MediaWiki（维基媒体软件）站点，包括 Wikipedia（维基百科）以及使用相同接口的 Wiki；网页抓取、普通搜索和以后其他资料库也通过同一来源接口进入资料集。

MediaWiki REST API（维基媒体表述性状态传递接口）提供页面搜索、页面内容、HTML（超文本标记语言）、历史和媒体链接，路径采用站点自己的 `/w/rest.php/v1/`；它适合普通搜索与页面读取。需要分类、反向链接或更广查询时使用功能更完整的 Action API（动作接口），但不把其复杂参数直接暴露给模型。官方接口要求客户端携带明确的 User-Agent（用户代理标识），并遵守速率、机器人和内容许可政策。

Wiki 学习流程为：

1. 用户给出主题、页面、语言或目标；
2. 连接器只执行小规模发现查询，返回候选页面、预计数量、修订时间和许可信息；
3. 学习预检展示计划抓取的页面上限、链接深度、估算词元、媒体策略和网络风险；
4. 用户确认后按页抓取，并以“站点＋页面编号＋修订编号”形成不可变来源快照；
5. 页面标题、章节、链接、修订编号、原始网址和许可进入文档快照；
6. 资料通读账本统一记录本地文件与 Wiki 页面，不因来源不同而改变完成标准。

Wiki 连接器必须遵守：

- 不做无边界递归爬取；页面数量、分类深度、链接深度和媒体下载均有硬上限；
- 不因页面互相链接而重复读取，按页面与修订去重；
- 默认只抓正文和必要元数据，不自动下载所有图片、历史版本或讨论页；
- 使用条件请求与缓存，尊重站点限流，发生 `429`（请求过多）时退避；
- 保存来源、修订和许可证，整理报告中的结论可以回到具体章节；
- Wiki 内容是外部资料而非系统指令，页面中的提示注入不能调用工具；
- Wiki 可能过时、有争议或被恶意编辑，跨来源冲突必须标记，不能把单页当成事实保证。

第一阶段不做 Wiki 编辑和账号写入，只提供只读搜索、导入、快照和学习整理。

## 五、工作区、成果、存档和记忆

### 5.1 会话工作区

每段对话拥有一个逻辑工作区，模型使用 `novex://`（Novex 内部资源协议）引用，而不是设备绝对路径：

```text
对话
├─ sources/     用户输入原件与资料集引用，只读
├─ notes/       文件笔记、分类、冲突和通读账本
├─ drafts/      AI 与用户共同编辑的草稿
├─ outputs/     已确认的文档、图片、地图和卡片
├─ saves/       文游存档与检查点
└─ derived/     解析快照、缩略图和搜索索引
```

应用内的“创作”目录按对话、类型和用户文件夹浏览这些成果；需要交给系统文件管理器时使用标准导出，不要求用户深入应用私有目录寻找。

### 5.2 文件工具

标准接口保留读取、创建和定点编辑能力，但只接受工作区引用：

- `workspace_inspect`（工作区检查）；
- `workspace_read`（工作区读取）；
- `workspace_write`（工作区写入）；
- `workspace_edit`（工作区定点编辑）。

内部可以暂时由 Minis 文件系统实现，模型不可见该事实。对二进制文件采用成果引用与专用转换器，不能把二进制内容塞进 JSON（结构化数据格式）。

### 5.3 存档与记忆

- 文游状态、快捷操作和存档跟随当前消息分支；切换分支不得重复执行工具或覆盖另一分支状态。
- `save_checkpoint`（保存检查点）写入结构化状态与可读摘要，而不是只保存一段无法校验的 Markdown。
- 长期记忆通过检查、提议、应用写入；对话蒸馏只引用已落库的事实，不把压缩摘要当作唯一原件。
- 世界、角色、文游、文档与创作成果可以被会话挂载；“作为背景引用”和“作为可管理对象”必须保持两套清晰语义。

## 六、少量缺陷的独立修复批次

工具层之外只处理已经有静态证据的窄范围缺陷，不借机重构全软件：

1. 对话作为初始路由时，左上角返回增加 Activity（安卓活动页面）结束兜底；
2. 右上角弹出菜单先完成关闭，再在生命周期恢复后执行跳转，避免旧对话按钮无响应；
3. 内容管理工具公布稳定的模块类型名称与合法值，错误不再出现 `u3.C0.rule` 一类内部信息；
4. 对话顶部栏、菜单和工具结果只经过 Novex 新组件入口，禁止新增直接 Material（安卓设计体系）原语。

正式修复前按项目规则再次确认这一批缺陷范围；页面视觉扩展、设置页全面翻修和其他 Minis 清理不混入本批提交。

## 七、测试驱动检查点

### 检查点 0：契约与失败基线

- 固化标准结果信封、稳定引用、风险等级和权限策略；
- 为 `.doc` 不支持、无标准文档工具、纯文本输出和大段自动注入写失败测试；
- 提交只包含领域接口与测试，不改变用户行为。

完成证据：标准结果信封、文档快照、受限检查／读取接口、附件收据、学习预检、确认快照和消耗上限均已进入独立 `novex-core`（Novex 核心）模块；十五项接口测试通过。当前只建立产品自有边界，不宣称真实 `.docx`（新版 Word 文档）、PDF（便携式文档格式）、旧 `.doc`（旧版 Word 文档）或 OCR（光学字符识别）解析已经完成。

### 检查点 1：文档快照与兼容解析器

- 让现有 `.docx`、PDF 等解析器输出内容块；
- 对旧 `.doc` 兼容路径做实验和失败状态验证，不把实验结果冒充已支持；
- 缓存按文件校验值与解析器版本失效；
- 保持原文件不变。

完成证据：现有 Android（安卓系统）文档提取器已通过薄 Adapter（适配器）接入 `novex-core`（Novex 核心）快照管线；兼容结果会形成有序标题、段落、列表和表格内容块，块编号由文件校验值和来源锚点稳定生成。缓存由 SHA-256（256 位安全散列算法）与解析器版本共同寻址；同一内容改名不重复解析，解析器升级会重新解析。真实 `.docx`（新版 Word 文档）桥接、原文件不变、空文档、图片型文档、损坏文档与旧 `.doc`（旧版 Word 文档）不支持状态均有自动测试。当前仍属于兼容桥接：复杂表格、图片资源、页码和原生结构保真度将在检查点 5 的流式 OOXML（Office 开放 XML 格式）解析器中补齐，不能把本检查点描述为完整文档格式支持。

### 检查点 2：标准文档工具

- 接入 `document_inspect` 与 `document_read`；
- 附件提示只注入文档收据、目录摘要和引用，不再默认注入 48,000／96,000 字符正文；
- 工具调用记录出现在消息下方，显示读取了哪个文档、标题或内容块。

### 检查点 3：学习预检、批量资料整理与通读恢复

- 小资料直接读取，大资料自动进入等待确认状态；
- 预检展示估算词元、费用风险、时间、网络、隐私和不支持项目；
- 未确认、计划已变化或超出确认预算时不能启动／继续学习；
- 支持一次加入多份超长文件并建立资料集；
- 文件解析并行受控，单个损坏文件不阻塞整批；
- 自动维护通读账本、精确重复和近似版本关系；
- 分层笔记在上下文压缩和应用重启后可恢复；
- 整理过程不创建或修改任何卡类对象；
- 用户明确要求转换后才产生可确认的内容提议。

### 检查点 4：Wiki 资料来源适配器

- 通过 MediaWiki REST API 搜索与读取页面，保留修订、来源和许可；
- 分类等扩展查询封装在 Action API 适配器后，不泄露复杂参数；
- 小规模发现后先预检，确认后才批量获取；
- 页面数、深度、速率和媒体均有限制；
- 本地文件与 Wiki 页面进入同一资料集、文档快照和通读账本。

### 检查点 5：轻量 `.docx` 解析器

- 实现流式 OOXML 解析；
- 与现有真实夹具逐块比较；
- 大文档基准达到预算后切为默认，POI 保持降级；
- 体积与兼容性证据充分后才删除重依赖。

### 检查点 6：工作区与创作成果工具

- 引入逻辑工作区引用；
- 文件创建、读取、编辑和导出不再依赖模型知道 Minis 路径；
- 图片、文档和地图进入统一成果库并保留来源分支。

### 检查点 7：内容管理、文游、存档与记忆

- 世界、角色、文游模块使用稳定类型；
- 共享内容写入保持提议、确认、原子应用；
- 文游快捷按钮、状态和存档按活动分支恢复；
- 记忆与对话蒸馏通过标准接口落库。

### 检查点 8：收回原始 Minis 工具

- 默认工具目录不再出现 Shell、设备绝对路径或数据库工具；
- Minis 只作为内部适配器；
- 受限计算能力通过工作区执行器按需提供；
- 完成回归后删除系统提示词中要求优先使用 Shell 和原始 `file_read` 的旧说明。

### 检查点 9：窄范围缺陷修复

- 单独提交对话返回、菜单跳转、工具错误与组件入口修复；
- 不与文档数据库迁移或工具契约提交混合。

## 八、自动验收矩阵

文档夹具至少包括：

- Microsoft Word、WPS、LibreOffice、Google Docs 导出的 `.docx`；
- 一份真实旧 `.doc`；
- 标题、多级列表、表格、链接、页眉页脚、脚注尾注、批注、文本框、修订和图片；
- 中文、英文、混合语言、空文档、损坏文档、加密文档；
- 超长正文、超大图片、压缩炸弹模拟、扫描 PDF。

行为必须验证：

- 同一文件只解析一次；
- 一次导入 100 份文件时，重复文件只保留一个解析快照，原始引用均可追溯；
- 标题、段落、表格和图片顺序稳定；
- `inspect`（检查）不泄漏全文；
- `read`（读取）分页无重复、无跳块，游标可恢复；
- 26 次连续文档查询不丢输入、不阻塞界面；
- 切换消息分支不会重复解析或重复执行外部副作用；
- 应用重启和上下文压缩后，批量通读从最后一个未覆盖内容块继续；
- 只做检索查询时不能把资料集状态错误标记为完整通读；
- 资料整理完成前后均不会静默创建世界、角色、分身或文游；
- 大资料未确认时模型调用次数为零，正文不会发送给模型提供商；
- 文件、模型、来源范围或预算变化后旧确认失效；
- 任务达到确认预算时自动暂停，不会继续产生不可见消耗；
- Wiki 发现查询不会越过页面与深度上限，重复页面按修订去重；
- Wiki 页面保存来源、修订和许可，断网或限流后可以恢复；
- 文档内容中的提示注入不能获得工具权限；
- 移除来源会话前检查共享成果引用；
- 解析失败有明确错误和可重试入口。

性能先在检查点 0 记录基线，再固定预算。最低硬要求是解析不在主线程进行、用户选择文件后立即出现可取消状态、长文读取每次输出受限、不会因整份解压或全文注入造成内存峰值和上下文突增。

## 九、构建、提交与人工验证节奏

- 每个检查点先写失败测试，再实现，再跑增量测试；
- 主线不反复安装和点击，只在一批完成后构建一次日常测试版；
- 日常测试版使用增量测试与不执行 R8（安卓代码压缩器）压缩的签名包；
- 正式候选版才运行完整测试、R8、体积和兼容性校验；
- 用户负责移动端点击验证；
- 每个检查点单独提交，文档解析、工具层、缺陷修复和视觉调整不混为一个提交；
- 未经用户明确要求，不发布、不修改正式分支和版本号。

## 十、明确不做

- 不把 Apache Tika（通用内容分析工具包）完整塞进 Android 应用；它覆盖面广，但依赖与运行体量不适合作为当前手机端基础能力。
- 不从零实现旧二进制 `.doc` 规范；先使用已有 HWPF 兼容适配器。
- 不一次把全文塞进模型，也不以“上下文足够大”为理由跳过检索与分页。
- 不允许模型用 Shell 猜数据库、枚举或应用私有路径。
- 不在这一轮顺手翻修所有页面、设置项或旧 Minis 功能。

## 十一、开工入口

压缩后从“检查点 0：契约与失败基线”开始。第一批只交付：

1. 标准工具结果信封；
2. 文档快照最小领域模型；
3. `document_inspect` 与 `document_read` 的失败测试；
4. 学习预检、确认快照和消耗上限的领域模型；
5. 证明旧的大段自动注入会被新接口替代的回归测试。

这五项通过后才进入解析器实现，不先改界面，也不先删除现有 POI 兼容路径。
