# Novex 开发与目录清理计划

更新日期：2026-09-01

## 一、当前判断

Novex 目前不是缺少开发速度，而是缺少稳定的“变更入口”和“发布分流”。从 0.1.8 到 0.2.0，新功能、兼容性修复、界面问题和发布工作连续进入同一条开发线，短期交付很快，但会产生三个后果：

1. 一个修复批次同时触碰聊天、模型、角色卡和发布流程，验证范围越来越大。
2. 新功能尚在内测时，稳定版修复也只能等待，或者被迫一起发布。
3. 回归测试数量在增加，但真实设备、流式界面和外部模型协议仍缺少分层验证。

代码热点也已经形成：`ChatViewModel.kt` 约 11,452 行，`ChatScreen.kt` 约 6,628 行，`StreamingMarkdownText.kt` 约 3,671 行。继续把新逻辑直接放进去，会让一次局部修改承担整条聊天链路的风险。

## 二、开发安排

### 0. 独立开发区

Novex 的源码、工作树、构建产物和验收材料统一收拢到一个专用目录，其他实验项目不再与其混放：

```text
Novex-Development/
├── repository/novex.git/     Git（版本控制系统）裸仓库
├── worktrees/
│   ├── stable/               稳定开发线
│   ├── preview/              预览开发线
│   └── tasks/                按问题临时创建的短期工作树
└── local/
    ├── builds/               本地构建产物
    ├── qa/                   验收截图与日志
    └── tmp/                  可再生成的临时文件
```

密钥继续存放在系统钥匙串、环境变量或 GitHub Secrets（GitHub 加密变量）中，不进入上述目录。

### 1. 两条发布线

- **稳定线**：只接收已经复现的缺陷修复、兼容性修复和低风险体验调整，版本使用 `0.2.x`。
- **预览线**：接收世界、角色卡、交互重做等新功能，版本使用 `0.3.0-beta.n`。预览版不阻塞稳定线发布。
- **紧急修复**：崩溃、数据丢失、无法登录、主要模型完全不可用等问题，从当前稳定版本直接修复并发布；随后同步回预览线。

目标分支结构：

```text
main                 已发布或随时可发布的稳定代码
next                 下一次功能版本的集成代码
fix/<问题>            从 main 创建的短期修复分支
feat/<功能>           从 next 创建的短期功能分支
v0.2.x                稳定版标签
v0.3.0-beta.n         内测预览版标签
```

迁移已经完成：`main` 是稳定线，`next` 是预览线；原 `work/novex-v1` 只作为短期兼容引用保留，不再触发重复构建，也不再用于日常开发。

## 下一轮已确认任务：对话媒体与滚动稳定性

以下问题已由真实设备截图确认并登记。本轮目录与发布通道整理完成后，下一轮修复前以此范围进行复现、诊断和验收，不与当前迁移提交混合：

1. 生成图片已经存在于应用附件目录，但对话消息只显示文件路径，没有渲染图片。
   - 对话内应直接显示图片预览。
   - 点击预览应能查看大图。
   - 图片菜单应提供“下载/保存到设备”和“打开所在位置”；若安卓版本或文件提供器不支持直接打开目录，则清楚提示并至少保证可保存与分享。
   - 不向用户暴露无法直接访问的内部沙箱路径作为主要交付结果。
2. 流式输出期间，即使用户没有滑动，列表也会被新增文字持续挤压或突然跳动。
   - 用户停留在阅读位置时，内容增长不得改变当前可见锚点。
   - 只有用户明确位于底部吸附区时才跟随新增内容；吸附距离需要以真实设备手势测试确定，并显著小于当前范围。
   - 上下跳转按钮、输入法弹出/收起、角色气泡高度变化不得误触发自动滚动。
3. 发送消息后偶发跳回前面数段内容。
   - 发送动作应稳定定位到新消息与新回复区域，不得跳到旧消息。
   - 需要覆盖普通对话、角色卡对话、长对话、输入法开启和流式回复五种场景。

验收必须包含滚动位置自动化回归测试和真实安卓设备录像复查；仅凭静态截图或“未复现”不能结案。

安卓端使用同一份源码生成两个相互隔离的应用：

- 稳定版：`com.noven.player`，名称为 `Novex`，只接受正式发布。
- 预览版：`com.noven.player.preview`，名称为 `Novex 预览版`，使用独立数据空间并接受测试发布。
- 预览更新使用 `.novex`（诺文预览更新包）扩展名，避免尚未升级渠道识别功能的旧稳定版把预览包误认为普通安卓安装包。

### 2. 缺陷批次不再按“收到时间”混装

每批工作先按同一条行为链归组：

- 聊天流式输出、滚动、输入框与键盘；
- 模型配置、连接检测与协议适配；
- 世界、玩家身份、角色卡与记忆；
- 附件、图片和文档解析；
- 更新、签名、安装与发布。

同一批只处理一条主链路。开始修复前明确“本批处理什么、不处理什么、验收结果是什么”，确认后再开工。新发现但不属于该链路的问题进入下一批，不临时塞进当前提交。

### 3. 需求和缺陷的完成标准

一个改动只有同时满足以下条件才算完成：

1. 问题能够稳定复现，或已有足够日志证明原因。
2. 修复落在拥有该行为的模块内，不把特殊判断散落到多个界面。
3. 至少增加一条能阻止同类问题回归的自动化测试；纯视觉或系统交互问题增加真实设备验收记录。
4. 相关定向测试通过，完整单元测试通过。
5. 候选安装包完成版本、签名和安全哈希校验。
6. 用户可见变化写入对应版本的简短更新说明。

### 4. 分层验证，不让每次小改动都重新打完整正式包

| 层级 | 触发时机 | 验证内容 | 目标 |
| --- | --- | --- | --- |
| A：本地定向验证 | 每次修改 | 改动模块的编译和相关测试 | 尽快发现直接错误 |
| B：持续集成验证 | 每次推送 | 完整单元测试、静态检查、调试构建 | 保证主线可合并 |
| C：候选版验证 | 准备内测或稳定发布 | 正式构建、签名、版本、安全哈希、模拟器冒烟测试 | 保证安装包可发布 |
| D：真实设备验证 | 涉及键盘、滚动、图片、文档、后台和安装 | 固定安卓设备用例 | 覆盖模拟器无法代表的行为 |
| E：真实模型协议验证 | 模型适配或定期执行 | OpenAI-compatible（开放人工智能兼容）、Gemini native（双子星原生）、OpenCode（开放代码）等真实请求 | 识别上游协议漂移 |

真实模型测试使用专门密钥和限次策略，不混入普通单元测试，也不因单一上游暂时故障阻断全部开发。

### 5. 小步拆分聊天主链路

不进行一次性大重写。以后修改相关行为时，顺手把该行为收拢到一个小接口后面：

- **TurnCoordinator（对话轮协调器）**：负责一轮请求、重试、工具结果和终止条件。
- **ResponseNormalizer（响应归一器）**：统一不同模型协议的文字、工具调用、结束原因、空响应和断流结果。
- **ConversationContextComposer（对话上下文组合器）**：明确组合通用对话、世界助手和角色对话的系统上下文。
- **StreamFollowController（流式跟随控制器）**：只负责用户是否位于底部、何时吸附、何时保持阅读位置。
- **RoleTranscriptRenderer（角色消息呈现器）**：负责角色头像、连续消息分组、玩家气泡和背景，不参与模型请求。

这些模块的接口同时作为测试入口。目标是以后修滚动只验证滚动，修角色头像只验证消息呈现，而不是每次都重新理解整个 `ChatViewModel.kt`。

## 三、建议发布节奏

- **紧急补丁**：满足紧急条件就发布，不等待其他功能。
- **普通稳定补丁**：积累一批同链路、已验证的修复后发布，建议每周一至两次，而不是每个问题单独发包。
- **功能预览版**：一个完整纵向功能可用后发布 `beta`（测试）版本，交给内测用户。
- **功能转稳定版**：预览版经过至少一轮真实设备和真实数据验证，且没有阻断级问题后，再并入下一稳定版本。

这样能继续更新，但不会让正在开发的角色卡功能绑住模型修复，也不会让一个紧急修复被迫携带尚未验证的新界面。

## 四、Novex 仓库目录清理计划

本节只定义计划，不立即删除文件。

### 1. 当前可见占用

| 位置 | 约占用 | 当前内容 | 处理建议 |
| --- | ---: | --- | --- |
| `artifacts/` | 376 MB | 历史调试包、正式包、界面截图 | 核对发布记录后清空安装包；有价值截图归档 |
| `dist/` | 169 MB | 0.1.2 至 0.1.6 的旧分发包 | GitHub Releases（GitHub 发布页）已有副本后清空 |
| 仓库根目录 `novex.apk` | 55 MB | 临时安装包 | 核对安全哈希后删除 |
| 仓库根目录 7 张未跟踪截图 | 小于 1 MB | 引导页、首页和启动页验收图 | 归档到版本化验收目录或移出仓库 |
| `.git/` | 164 MB | Git（版本控制系统）对象和历史 | 暂不处理；分支标签审计后再压缩 |

第一阶段预计可释放约 **600 MB**，不触碰源代码和正式发布记录。

### 2. 分类规则

**可直接再生成**

- `artifacts/` 和 `dist/` 中已经上传发布页的安装包；
- Gradle（安卓构建系统）的 `build/`、`.gradle/`、`.cxx/` 等缓存；
- `.DS_Store`（macOS 文件夹元数据）；
- 临时下载、测试报告和本地调试截图。

这类文件不进入版本控制，可由清理脚本删除。

**需要先归档**

- 唯一的真实设备缺陷截图；
- 尚未整理进测试用例的研究结果；
- 未上传发布页的签名安装包及其 `SHA-256`（安全哈希算法）文件；
- 能证明特定版本行为的验收资料。

建议统一存放为：

```text
docs/qa/<版本>/<功能或问题>/
docs/research/<主题>.md
```

大体积安装包不放进 Git（版本控制系统），只保存在 GitHub Releases（GitHub 发布页）及其持续集成构建产物中。

**禁止清理**

- `src/android/app/libs/` 中当前构建依赖的 AAR（安卓归档）和 JAR（Java 归档）文件；
- `src/android/app/src/test/resources/docx/` 和 `androidTest/assets/docx/` 的真实文档样本；
- `deps/` 中无法重新下载或项目明确要求保留的加载器与补丁；
- 未提交、未备份或来源不明的文件；
- 发布签名材料和密钥。密钥只保存在安全存储中，不能进入清理归档或版本控制。

### 3. 执行顺序

1. 列出目标文件、大小、安全哈希和对应发布版本，生成清理清单。
2. 对照 GitHub Releases（GitHub 发布页）确认正式安装包、签名和安全哈希均可下载。
3. 将需要保留的截图和研究文件归档到明确目录并提交。
4. 先把可再生成文件移动到系统废纸篓，保留一个短暂恢复窗口。
5. 重新运行完整单元测试和一次正式构建，确认清理没有移除隐含依赖。
6. 再清空废纸篓，并记录实际释放空间。

### 4. 后续自动化

增加一个默认只预览、不立即删除的本地清理脚本：

```text
scripts/clean_local_workspace.sh --dry-run
scripts/clean_local_workspace.sh --apply
```

脚本只允许处理 `.gitignore`（Git 忽略规则）明确覆盖的生成物，并在执行前输出绝对路径、文件数和预计释放空间。`--apply` 模式也不得处理未跟踪但未被忽略的文件。

持续集成中继续只保留 30 天安装包和 14 天失败测试报告；正式版本长期保存在 GitHub Releases（GitHub 发布页），本地 `dist/` 不再承担历史仓库职责。

## 五、工作区其他项目的第二阶段清理

Novex 仓库之外，当前工作区四份 `deepseek-harness`（深度求索工具框架）目录的 `node_modules`（本地依赖目录）合计约 **5.4 GB**。其中三份存在未提交修改，不能删除项目目录。

第二阶段只考虑：

1. 确认哪些副本仍在使用；
2. 为所有未提交修改建立提交或补丁备份；
3. 关闭相关开发任务后，仅删除可重新安装的 `node_modules`（本地依赖目录）；
4. 删除前确认锁定文件存在，并记录恢复命令；
5. 最后再评估是否把重复副本统一为 Git worktree（Git 工作树），不直接合并或覆盖不同实验分支。

这一阶段预计还能释放约 **5.4 GB**，但必须与 Novex 仓库清理分开执行。

## 六、下一步执行建议

1. 先执行 Novex 仓库第一阶段清理，目标约 600 MB。
2. 增加安全的本地清理脚本和目录说明。
3. 将当前发布分支迁移成稳定线与预览线，保留现有自动更新能力。
4. 从下一次真实缺陷开始执行“同链路批次＋回归测试＋分层验证”。
5. 第一个结构治理目标选择流式跟随，因为它反复出现、用户感知强，也最适合先建立独立模块接口。
