# 本轮关系打通更新：酒馆借鉴与双向交换建议

本记录以用户本轮完整交接为准，重排此前研究中的优先级。正文区分“已经确认的本轮边界”和“基于酒馆研究提出的建议”。新增建议后来已获用户确认；本文保留研究阶段的建议语气，实际实施状态以更新计划为准。研究基础见[三类卡片与酒馆研究](/Users/noven/Documents/Codex/CodexProduct/1/Novex-Development/worktrees/preview/docs/research/preview-cards-and-sillytavern-2026-09-06.md)。

**已经确认的本轮主线**

让人工智能明确当前回答身份、正在使用的设定、获准管理的对象、工作空间中的内容及相互关系，并使这些关系持久保存、可查、可恢复。同一对话可以同时游玩和创作；回答身份、背景、管理范围、活动文游与呈现不能相互替代。

以下均继承用户确认：

- 一段对话只有一个主要回答身份和至多一个活动文游；默认 Nova（诺娃助手），独立人格是职责预设，角色身份指向具体版本。仅加入背景或管理对象不能自动换身份；只管理文游不能启动文游。工具按实际能力及访问范围提供，回答身份不构成授权。
- 对话保有自己的提示词，可继续编辑而不反写原件；图片生成提示词继续保留。启动文游采用其指定身份，未指定时用游戏主持人。
- 新对话附带私有世界、角色、文游空草稿和工作空间；空卡不进入全局库，不自动启用，不自行触发创作。成功写入即持久保存。返回列表时清理没有内容且没有保护性引用的私有空卡；非空作品进入对应管理空间，保留来源。运行任务与待确认写入保护其目标；共享卡、导入卡和被引用媒体不按空草稿规则清除。
- 世界、角色版本、文游及模块／条目用稳定编号互相引用，明确背景、回答身份、玩家身份、规则、管理等用途。保留正反向索引，处理循环、缺失依赖、删除影响和交换时编号重映射。引用不传递权限，不隐式启动第二文游，本局采用的快照不静默更新。
- 角色配套玩家身份只在适用的扮演场景使用；角色仅作背景时，读取、搜索、摘要和提示词路径都须隔离配套身份与专属扮演指令。管理访问单独判断。身份冲突不无提示覆盖。
- 本体、人生阶段、平行分身、编辑修订分别表达；先做可靠列表与索引，再做局部关系图。角色版本之间不自动同步知识和记忆。
- 明确要求原生卡片时直接进入原生创作流程，主动选择合理模块和技术字段。文游可以只有规则与开局共创，不强求已有世界与角色。常规整理不反复询问；真实冲突、受保护写入等依现有边界处理。空容器不等于完整作品，抽样不等于全文通读。
- 工作空间成果、长文覆盖进度、本局状态、存档和记忆真实保存并可追溯；按结构读取而不全量灌入上下文。查看状态不推进剧情，执行行动形成相应回合。
- 复用 JSON（结构化数据）或 Markdown（标记文本）编辑及现有展示、保存、预览；特殊模块呈现、多角色独立发言继续延期。

研究核对时只完成第一小步：独立人格快照持久化及身份格式统一等基础，用户交接说明云端增量测试通过；这不是全链路完成。当时本地核对最新提交为 `3c8b8c5`，没有重新运行测试。

后续用户已确认：明确结束文游恢复启动前的回答身份和玩家身份；返回列表不等于结束文游。

**酒馆研究应怎样改变本轮方案**

建议把酒馆视作同一内容系统的外部输入输出端。诺文继续用已经确认的对象与权限关系管理作品，转换层负责解释外部卡片。这样可以借用酒馆成熟的创作方法，同时保留诺文多卡复用、带用途引用、原生工具、私有草稿和作品归属等优势。

需要区分两条线：

| 线 | 建议本轮纳入的内容 | 后续可以逐步实现的内容 |
| --- | --- | --- |
| 方法借鉴 | 区分定义、触发、状态、呈现；明确字段用途和生效范围；实际引用记录；样本验证 | 更复杂的触发控制、创作调试界面 |
| 双向交换 | 原始数据留存、稳定对象映射、依赖关系、兼容能力说明所需的数据基础 | 逐项完成酒馆格式读取、写回和行为兼容；第三方脚本支持单独评估 |

这里调整了此前“先完善游玩、最后再考虑互通”的排序：字段用途和交换保留方式会影响本轮空卡、引用与工具设计，需要现在考虑；完整生态兼容不能挤掉已确认主线。

酒馆的角色定义、世界书和提示词管理分别处理内容与生成规则；世界书可有作用域和触发条件。它的玩家身份描述用户，而本轮独立人格描述人工智能职责。由此得到的设计要求是：每个导入字段都需要明确“谁读、什么时候读、用于什么”，不能只留下一个正文文本。[角色设计](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)、[世界书](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)、[玩家身份](https://docs.sillytavern.app/usage/core-concepts/personas/)、[提示词管理器](https://docs.sillytavern.app/usage/prompts/prompt-manager/)

**建议的双向通道**

酒馆作品 → 保存原件及解析结果 → 按用途映射为诺文对象／模块／引用 → 在统一对话中使用或管理 → 按选定来源版本导出酒馆可表达的内容，并说明差异。

1. **导入先保留作品，再转换。** 原卡、来源格式及版本、作者说明、未知字段与扩展、资源和规则需要保留。外部原件属于工作空间可定位的来源材料；它不因为导入就获得当前系统指令或编辑权限。原始资料的读取也要遵守场景隔离，不能借“原文查看”向背景读取路径泄露配套身份与扮演指令。

2. **可识别字段按用途进入现有结构。** 单人物卡通常映射到角色根对象与本体；已有明确背景条目可保留为模块或设定条目。酒馆角色卡也可能承载主持人或整套文游，不能仅凭文件类型或名字强制分类。明确的用户创作要求优先；无法可靠区分时保留来源、暂不激活冲突用途。

3. **引用承担组织，触发规则承担每轮选择。** “文游使用这个世界”是一条可查的内容关系；“本轮提到帝议所以读这个条目”是一次选择结果。两者分别保存。条目触发只发生在当前合法候选范围内，不能从命中词推导出新的读取或编辑授权。

4. **使用与管理采用不同读取视图。** 使用侧从本局选定版本与允许的字段装配上下文；管理侧按授权定位可编辑原件及修订。来源归档、搜索、摘要、预览、工具读取和提示词装配应采用一致访问规则。管理时改了原件，不应使本局模型下一轮偷偷读到更新内容。

5. **导出形成交换版本。** 一个角色版本可以导出为一张酒馆角色卡，相关背景转成其支持的世界书条目。诺文的多世界关系、人生阶段和文游结构没有直接对应时，应以可兼容内容加扩展记录／依赖清单表达，避免伪称酒馆本体认识这些关系。可尝试把纯提示词驱动的文游导出成主持卡加世界书，但必须验证行为；确定性工具、原生存档和状态操作不能只改成一段说明就称兼容。

6. **返回导入可对照来源。** 记录这次导出的来源对象、修订和字段映射，供再次导入时识别候选对应关系。编号只在明确的来源命名空间中解释；不按名称绑定，不信任外部文件声称的本地身份。默认保留独立导入结果；更新已有对象时沿用受保护变更流程，并展示冲突。

酒馆第二版角色卡规范明确要求保留未知扩展数据；这可以作为交换设计的最低基础。保留原数据、可往返编辑、可复现执行是三种不同能力，应分别记录。[角色卡第二版规范](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/spec_v2.md)

**本轮最值得接入的三个位置**

| 位置 | 建议补充 | 直接解决的问题 |
| --- | --- | --- |
| 私有空卡与工作空间 | 保留草稿的来源、生成任务、内容覆盖范围和交换信息；引用可以定位整理笔记和原件 | 人工智能知道写到哪里，何时算写完，压缩后能继续；卡片与文件不脱节 |
| 带用途互引 | 内容用途与字段访问范围可表达；记录使用的来源修订／快照；保留外部依赖但不擅自激活 | 放入角色资料不抢主持人身份；编辑原卡不悄悄改变本局；未支持字段不被提前压平 |
| 标准工具 | 工具可读到经授权的对话关系摘要、目标索引和兼容能力；写入结果返回真实对象、模块及落盘结果 | 人工智能不再靠猜测当前身份和卡片目标，也不把创建容器当作完成正文 |

对话关系摘要应由软件当前状态生成，包括回答身份、玩家身份、背景来源版本、活动文游、本局分支、可管理目标和工作空间索引。核心摘要进入上下文，完整内容按工具定位。身份与权限无需模型从长对话里自行推断。

不建议新设一个“酒馆创作模式”或第四类顶层卡片。导入、学习、整理、原生创作继续在统一对话中完成；对酒馆方法的学习通过来源可查的整理笔记与显式创作转化实现，不自动修改全局人格或其他项目的写作规则。

**用《生生》贯通一次完整流程**

这是建议的验收样例，不是已经创建的卡片：

- 用户在普通对话要求“把这些做成文游卡”。Nova（诺娃助手）仍是回答身份，使用私有文游草稿及工作空间。能直接依清楚章节组织模块；材料未通读完成时保留覆盖记录。
- 《生生》可以先只有“开局共同建世界”和规则，不必为了填满三个草稿而制造世界与角色。
- 当用户确有对应内容时，将“生生之学”作为背景引用、“伏生”具体版本作为参考人物、“帝议”作为规则条目；记言人是玩家身份。仅创建和管理这些对象不启动游戏。
- 用户明确启动后，使用指定身份或默认游戏主持人，按规则处理已有玩家身份冲突，并固定本局采用的内容。伏生仍是参考人物时，不加载其专属扮演指令及配套玩家身份。
- 游玩中用户要求“完善帝议规则”，在已有授权范围内定位共享模块并形成变更；本局保留原快照。是否采用新规则是单独、可见的操作。
- 返回列表时，已写入作品保留，受保护空卡继续保留，其他空卡清理；不结束文游，也不切换回答身份。
- 用户选择导出酒馆版本时，输出可表达的主持指令、开场与世界书，以及本版本的兼容说明；默认不混入私人对话、长期记忆和本局存档，除非用户明确选择导出这些内容。

**把“借鉴”变成可验证的积累**

建议建立少量来源清楚的样例：普通人物卡、条件世界书、主持型文游卡、带第三方依赖的卡。每个样例分别记录原始结构、诺文映射、预期触发、实际引用和交换后差异。

可先自动验证身份不变、权限过滤、字段保留、依赖重映射、空草稿恢复与状态分支；真实模型验证再检查文风、开场和规则执行。不同模型、预设与历史会影响输出，比较时保持这些条件可追溯。样例是长期积累的方法，不应把自动测试通过写成与酒馆游玩效果相同。

酒馆内置脚本、酒馆助手及变量更新框架已经展示了按钮、变量与呈现分离的价值；本轮优先映射到我们的标准工具和本局状态，第三方脚本兼容列明依赖和未支持部分。[酒馆脚本](https://docs.sillytavern.app/usage/st-script/)、[酒馆助手](https://n0vi028.github.io/JS-Slash-Runner-Doc/)、[变量更新框架](https://github.com/MagicalAstrogy/MagVarUpdate)

**交付边界**

研究阶段当时只保存这份建议与更新旧研究的优先级，没有修改产品代码、已确认计划或版本号；后续实施进度见更新计划。当前新版三库导入仍为原生卡包；旧酒馆解析器会把世界书合成文本，不能作为上述通道已经实现的依据。新的双向交换建议需要在实现中逐项验证；结束身份策略已由用户后续确认，并在实现计划中记录。
