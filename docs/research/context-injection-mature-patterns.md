# 超长世界设定与角色卡的成熟上下文注入机制

## 结论先行

Novex（新产品层）不应把几万字世界卡或完整角色卡在每轮请求中全部发送给模型。成熟方案的共同点是把内容分成两层：

1. 少量、稳定、每轮必须存在的核心信息；
2. 大量、按当前对话相关性临时取出的设定条目。

同时，Novex（新产品层）必须把以下两个概念分开：

- **回答人格**：本轮由 Nova（通用助手人格）回答，还是由某个角色版本扮演回答；
- **参考资料**：世界卡、角色卡、玩家身份和其他文档中，哪些内容只作为背景事实提供。

因此，同一张角色卡应有两种独立用法：

```text
扮演模式：角色版本占据“回答人格”位置，模型以该角色回应
参考模式：角色版本进入“知识来源”位置，Nova 仍然回答，只把该角色当作世界人物
```

两种模式可以复用同一份角色数据，不需要复制两张卡。差异只存在于对话上下文的关联方式。

## 一、SillyTavern（酒馆）的做法

### 1. World Info（世界信息）不是整本常驻，而是动态字典

SillyTavern（酒馆）官方把 World Info（世界信息，也称 Lorebook／设定集）定义为动态提示词系统：条目通常由关键词命中后才加入提示词。世界信息还可以分别绑定到全局、角色、玩家身份或单个对话；多个来源在生成时合并并按插入顺序排序。[SillyTavern World Info（酒馆世界信息）官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

这意味着成熟方案并不把“世界卡是否启用”理解成“整本世界卡是否全部发送”，而是把它理解成“哪些设定条目有资格参与本轮检索”。

### 2. 关键词触发和扫描深度

每个条目可以有主要关键词、附加条件和正则表达式（Regular Expression，规则表达式）。全局 Scan Depth（扫描深度）决定回看最近多少条消息：0 表示不从普通消息触发，1 表示只扫描最后一条，2 表示扫描最后两条，以此类推。中文、日文等不以空格分词的语言不适合默认开启整词匹配。[SillyTavern World Info（酒馆世界信息）官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

对 Novex（新产品层）的启示：中文第一版应支持“名称＋别名＋用户关键词”精确触发，但不能依赖英文式整词边界。扫描对象应以最近消息和当前活动实体为主，而不是每轮扫描整段对话。

### 3. 常驻条目和明确预算

SillyTavern（酒馆）允许把少数条目标记为 Constant（常驻），无需关键词也会加入；同时用 Context Percentage / Budget（上下文比例／预算）限制所有世界信息在一次请求中最多占多少词元。预算耗尽后，即使还有关键词命中，也不会继续加入。常驻条目优先，然后才按条目顺序和直接命中优先级分配剩余预算。[SillyTavern World Info（酒馆世界信息）官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

这直接回答了“几万字世界卡怎么办”：只有世界核心规则需要常驻，其余内容必须竞争一个有限预算。

### 4. 递归关联必须有停止边界

SillyTavern（酒馆）的 Recursive Scan（递归扫描）允许一个已触发条目的正文再次触发其他条目。例如“贝茜是鲁弗斯的朋友”可以继续带出“鲁弗斯”的设定。它同时提供不可被递归触发、触发后停止递归、延迟到递归阶段，以及 Max Recursion Steps（最大递归步数）等限制，避免关联无限扩散。[SillyTavern World Info（酒馆世界信息）官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

对 Novex（新产品层）的启示：地区、势力、事件、角色之间的结构化引用正适合做一次关联扩展，但默认不应无界递归。第一版建议只允许“一次直接命中＋一次关系扩展”，仍受同一词元预算约束。

### 5. 短期持续激活解决代词和场景延续

SillyTavern（酒馆）提供 Sticky（粘附）、Cooldown（冷却）和 Delay（延迟）等按消息计数的时效效果：条目命中后可以继续保持若干条消息，不必每轮重复说出关键词；这些状态只属于当前对话，分支继承父分支状态。[SillyTavern World Info（酒馆世界信息）官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

这对“他”“那里”“那场战争”等连续指代很重要。Novex（新产品层）可以保存一小组当前场景实体，并让最近命中的人物、地点和事件短期保持活跃；该状态必须属于消息分支和上下文版本，切换分支时不得串线。

### 6. 关键词和向量匹配可以并存

SillyTavern（酒馆）的 Vector Storage Matching（向量存储匹配）用最近若干消息与条目正文的嵌入相似度替代关键词命中，但最大返回条目数并不取代世界信息的词元预算；概率、角色过滤、互斥组等其他规则仍然生效。官方还明确提醒，向量结果不可完全预测，需要确定性时应使用关键词。[SillyTavern World Info（酒馆世界信息）官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

所以 Novex（新产品层）不应在“关键词”与“向量检索”中二选一。角色名、地名、专有名词适合确定性命中；抽象询问、同义表达和长篇创作需求适合语义召回。

### 7. Data Bank（资料库）采用分块检索

SillyTavern（酒馆）的 Data Bank（资料库）把资料分成全局、当前角色和当前对话三个作用域。启用 Retrieval-Augmented Generation（检索增强生成）后，长文档会分块，只把最相关片段加入提示词；配置包括分块大小、相邻重叠比例、最多取回块数、最近多少条消息组成检索问题、相关度阈值、注入模板和注入位置。跨多个文档的返回块共享一个总额度。[SillyTavern Data Bank（酒馆资料库）官方文档](https://docs.sillytavern.app/usage/core-concepts/data-bank/)

这非常适合 Novex（新产品层）的长篇自由文本，但世界的结构化模块不应先被拍平成一个巨型文本文件。模块和条目本身就是天然边界，只有单条内容过长时才需要再次分块。

## 二、角色卡在成熟方案中的成本与局限

SillyTavern（酒馆）把角色名称、描述、性格和场景视为 Permanent Tokens（常驻词元），每次生成都会发送；首条问候只在对话开始发送，示例对话则在空间不足时逐块退出上下文。官方明确提示：角色定义越大，可用于聊天历史的空间越少。[SillyTavern Character Design（酒馆角色设计）官方文档](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)

它还允许角色卡覆盖 Main Prompt（主提示词／系统提示词）和 Post-History Instructions（历史后指令），因此传统角色卡天然倾向于“让模型扮演这个角色”。与此同时，SillyTavern（酒馆）的主提示词也可以把模型设成通用助手、写作伙伴、叙述者或虚构角色。[SillyTavern Prompts（酒馆提示词）官方文档](https://docs.sillytavern.app/usage/prompts/)

对 Novex（新产品层）的判断是：可以借鉴它的字段分层和预算机制，但不能照搬“选中角色卡就必然由该角色回答”的绑定。用户已经明确需要：

- Nova（通用助手人格）可以在世界背景下共创；
- Nova（通用助手人格）可以把某张角色卡当作故事资料，而不是自身人格；
- 必要时才把回答人格切换为具体角色版本。

因此“回答人格”和“参考角色”必须是两个字段，而不是一个 `characterId（角色编号）` 同时承担两种语义。

## 三、NovelAI（小说人工智能）的补充做法

NovelAI（小说人工智能）的 Lorebook（设定集）同样采用激活键：命中最近故事文本才注入；支持 Always On（始终开启）、正则表达式、多关键词同时出现、Search Range（搜索范围）、Cascading Activation（级联激活）、Token Budget（词元预算）、Reserved Tokens（预留词元）、插入位置和无法完整容纳时的裁剪规则。[NovelAI Lorebook（小说人工智能设定集）官方文档](https://docs.novelai.net/en/text/lorebook/)

它提供的两个有用补充是：

1. 高优先级条目可以先预留空间，避免关键世界规则被普通条目挤掉；
2. 条目可以设置为“不可裁剪”，空间不足时宁可整条不放，也不把半段规则塞进去造成歧义。

Novex（新产品层）可据此为条目增加“必须完整”“可以摘要”“可以截取片段”三种装配策略，而不是统一按字符硬截断。

## 四、规模更大时的混合检索

OpenAI（开放人工智能公司）的 Vector Store（向量存储）接口把文件切分策略作为显式配置；当前自动策略使用 800 个词元的最大块和 400 个词元重叠，也允许自定义块大小与重叠。检索接口还支持属性过滤、最大返回条数、重新排序、相关度阈值和问题改写。[OpenAI Vector Stores（开放人工智能向量存储）官方文档](https://platform.openai.com/docs/api-reference/vector-stores)

Anthropic（安思罗匹克公司）建议大知识库采用混合检索：BM25（最佳匹配二十五算法）负责精确词语，Embeddings（嵌入向量）负责语义相似，再合并、去重并重新排序。其 Contextual Retrieval（上下文化检索）还会在分块前给每块补充一小段来自整篇文档的定位信息，避免“这家公司”“那一年”之类脱离原文后失去含义。官方同时指出，取回更多片段虽能提高召回，但过多信息也会干扰模型，必须用实际评估选择数量。[Anthropic Contextual Retrieval（安思罗匹克上下文化检索）官方文章](https://www.anthropic.com/engineering/contextual-retrieval)

对 Novex（新产品层）的具体含义：

- 先按当前世界、角色版本、对话和消息分支做元数据过滤；
- 再用角色名、地名、别名等做精确召回；
- 同时用语义相似度补回没有显式关键词的相关条目；
- 合并后按“常驻级别、直接命中、结构化关系、语义得分、最近活跃状态”重新排序；
- 最后才按统一预算装配到模型请求。

## 五、建议给 Novex（新产品层）的上下文模型

### 1. 四个互相独立的槽位

```text
回答人格
├─ Nova（通用助手人格，默认）
└─ 某个角色版本（本体或分身）

知识来源
├─ 零个或多个背景世界
├─ 零个或多个参考角色版本
├─ 零个或一个活动文游
└─ 对话附件或其他资料

玩家身份
└─ 可选玩家身份

任务与工具
├─ 普通交流
├─ 共创、检查、改写等当前意图
├─ 零个或多个管理对象
└─ 本轮可调用工具
```

第一阶段仍可保持“一段对话最多选择一个扮演角色”，但不应限制参考角色的数量。参考角色只是知识实体，不等于多角色共同对话。

多个背景世界必须保持各自的世界边界和模块命名空间。它们可以共同构成跨世界叙事，但不能因为字段或专有名词相似而被静默合并；后加入的世界也不能覆盖先加入的世界。

管理对象与知识来源是两种独立关系。前者界定人工智能可以定位和管理哪些世界、角色、文游或文档，不表示这些内容自动成为故事背景，也不表示其完整正文每轮都会进入模型上下文；同一对象可以同时具有两种关系。

### 2. 世界卡的三层存储与注入

```text
世界核心层
  世界名称、极短概述、不可违反的全局规则
  → 少量常驻

结构化设定层
  地区、势力、种族、事件、时间线节点、角色版本引用
  → 关键词＋结构化关系＋语义检索

长文与媒体层
  长篇章节、地图说明、附件、图片说明
  → 分块检索；图片本体默认不进入文本模型上下文
```

封面、标志、背景图纯粹用于呈现。地图第一阶段可以是一张图片和说明；只有说明文字参与普通检索。未来支持视觉模型时，也应只在用户讨论地图或主动查看地图时附带图片，不应每轮发送。

### 3. 每轮装配流程

```text
当前用户消息＋最近若干条活动分支消息
                ↓
识别明确专名、别名、当前场景实体和任务意图
                ↓
按对话关系分别确定背景设定、管理对象和附件范围
                ↓
常驻核心 + 精确关键词召回 + 语义召回
                ↓
做一次结构化关系扩展，去重并重新排序
                ↓
在独立词元预算内装配，记录本轮实际使用的来源
                ↓
与回答人格、玩家身份、记忆、活动消息路径和工具说明合并
```

检索只读取资料，不执行任何工具，也不产生外部副作用。切换消息分支时，根据该分支的上下文版本重新计算；不得因为切换分支重新执行历史工具。

### 4. 预算建议是起始参数，不是永久规格

以下数值是基于上述成熟机制给 Novex（新产品层）的产品建议，不是任何官方方案的固定答案：

- 普通对话：世界与参考角色资料合计最多占可用上下文约 10%～15%，并设置约 4,000 词元硬上限；
- 深度共创：用户主动开启后可提高到约 20%～25%，但必须明确显示会增加请求成本并压缩历史空间；
- 世界核心和当前回答人格优先预留；
- 直接提到的实体优先于语义相似条目；
- 一条设定放不下时优先使用人工摘要或整条跳过，不默认截成可能改变含义的半段；
- 具体比例必须通过中文角色扮演、普通问答和长篇共创三类评估再调整。

即使模型支持很长的上下文，也不应默认全量发送。长上下文会增加费用和延迟，并可能让无关信息干扰当前任务；它更适合作为预算上限，而不是取消检索的理由。

### 5. 让用户看见模型实际拿到了什么

SillyTavern（酒馆）提供查看最终提示词的方法；NovelAI（小说人工智能）的 Context Viewer（上下文查看器）则进一步显示每个条目的来源、是否被纳入、纳入或排除原因、触发键、预留和实际词元量、裁剪方式与插入阶段。这对排查“模型为什么忘了某条设定”非常重要。[SillyTavern Prompts（酒馆提示词）官方文档](https://docs.sillytavern.app/usage/prompts/)、[NovelAI Context Viewer（小说人工智能上下文查看器）官方文档](https://docs.novelai.net/en/text/editor/advancedsettings/)

Novex（新产品层）应在回复菜单中提供“本轮上下文”只读视图，至少显示：

- 当前回答人格；
- 启用的世界和参考角色；
- 实际注入的设定条目及来源；
- 每部分使用的词元量；
- 哪些命中因预算不足被跳过；
- 是关键词、关系还是语义检索触发。

这比让用户猜测“整张卡到底有没有生效”更可靠，也便于后续调试和自动评估。

## 六、推荐实施顺序

1. 先把领域关系拆成“回答人格”和“知识来源”，默认回答人格固定为 Nova（通用助手人格）。
2. 世界模块和角色模块增加稳定条目编号、别名、常驻级别、优先级、完整性策略与结构化引用；暂时不要强迫普通用户填写复杂检索参数。
3. 第一版实现确定性检索：最近消息扫描、中文别名命中、一次关系扩展、短期活跃实体、统一词元预算。
4. 接入“本轮上下文”检查器并记录每次装配结果，先建立可解释基线。
5. 内容规模和真实语料足够后，再加入本地或云端 Embeddings（嵌入向量）和 BM25（最佳匹配二十五算法）混合检索；向量索引必须记录模型版本，模型变化时重建。
6. 最后再让创作工具通过同一领域命令生成或修改条目；工具生成的内容先成为草稿，不得绕过预览直接改变世界卡或共享角色版本。

## 最终判断

Novex（新产品层）应该借鉴酒馆的“世界信息按需激活”，但不应照抄酒馆以角色卡为中心的对话身份绑定。更适合 Novex（新产品层）的设计是：

> Nova（通用助手人格）或具体角色版本决定“谁在回答”；世界卡和任意角色卡决定“本轮允许参考哪些事实”；上下文检索器决定“几万字资料中当前真正需要哪几段”。

这样普通对话、共同创作和角色扮演仍然是一种统一对话，只是回答人格与知识来源配置不同。
