# 结构增量复核：统一保存、卡片包与历史范围

当前状态以[3.0 故障表](3.0-bug-board.md)和文末增量为准；下文原复核保留，不用旧的“尚未完成”覆盖已验证修正。

日期：2026-09-09。对象为 `preview-icon-memory`（当前修复工作树）的本地未提交代码。此次仅阅读新模块、调用点与测试，没有改生产代码、运行构建或操作测试主机；以下结论不代表新增代码已通过验收。

## 结论

三项拆分方向成立：

- `NovexConversationSettingsStore`（对话设置存储）统一了配置互斥、数据库事务、采用快照、保存和提交后的界面安装；主要入口已接入，不再逐个拼保存过程。
- `NovexCardImporter`（卡片导入器）使用原存储接口，不自行开启事务；`NovexCardExporter`（卡片导出器）只接收快照与读取接口；`NovexCardTransferFields`（卡包共用字段）没有存储副作用。未发现这次拆分新造了第二套卡片提交。
- `NovexScopedConversationHistory`（按访问范围投影的历史）不改历史原件，只改变发送给模型的内容；当前保存回执投影仅提取白名单工具结果中的卡片编号和名称，并检查当前管理对象编号。已读代码中没有直接把被过滤的正文、调用参数或推理塞回回执。

仍有下列三项具体修正／验收建议。路径除特殊注明外，均相对于 `src/android/app/src/main/java/com/openminis/app/`（安卓生产源码根）。

## 1. 统一写入回执格式，补齐旧计划与模块操作的续作记录

**确定的接口不一致，优先处理。**

`novex/adapter/NovexScopedConversationHistory.kt:64` 虽然允许 `novex_apply_content_changes`（执行内容变更），第 66—68 行却只接受 `saved`（已保存）、`status`（状态）、`created_cards`（已创建卡片）／`updated_cards`（已更新卡片）。实际 `novex/domain/NovexContentToolExecutor.kt:40` 的计划执行分支返回 `created_subjects`（已创建对象）及 `readback_status`（回读状态），没有这些必需字段。因此，该分支真实成功后再改身份，其成果编号仍会被移除，白名单并没有使它获得连续性。

同时，`novex/domain/NovexCardFileService.kt:23` 支持写模块、移动模块、关联卡片，第 72—73 行返回 `saved_modules`（已保存模块）与 `saved_references`（已保存引用）；历史投影没有接纳这些操作。卡片创建不会因此丢失，但“该模块已经补充／该关联已经建立”的工作状态仍会丢失。

建议由宿主写入链提供统一的、无正文的成果回执，而不是在历史函数中继续增加各种结果文本判断。旧计划可保留“已写入、未回读”状态，不能抬高成“已核验”；模块和引用只保留允许范围内的对象编号、模块编号、操作状态，正文重新读取。增加身份／玩家切换后的旧计划创建、模块追加、排序、关联测试，并验证移除管理对象后相应回执也消失。不要通过恢复原始工具结果解决续作问题。

## 2. 保留一个最外层提交，但把来源准备移到事务之外

**已确认的调用结构问题，实际卡顿程度尚未测量。**

`ui/chat/ChatViewModel.kt:8821` 先进入设置存储的更新事务，再调用内容执行器；执行器 `NovexContentToolExecutor.kt:29` 又包事务，并在第 48 行进入卡片文件服务；后者第 19 行注释称“来源解析在写入事务之前”，实际已处于前两层事务中。

`NovexCardFileOperations.kt:22` 会按整份文档组织章节，`NovexCardSourceModules.kt:11` 读取来源修订，`src/android/novex-core/src/main/kotlin/com/openminis/app/novex/domain/FileNovexDocumentSnapshotRepository.kt:38`（核心模块文档存储）会读文件和校验修订。因此，大资料读取及章节组装现在也占着设置锁与数据库事务；其他保存可能被长时间阻塞。

这不是已证明发生了分裂提交：当前传入的事务仍是同一个 Room（安卓数据库映射库）数据库。建议明确“准备不可变操作 → 在当前范围内再次校验 → 单次提交卡片与配置 → 返回已提交回执”四个步骤。来源文件读取和纯字段展开在准备阶段完成；事务内部重新验证范围、对象修订和计划状态。不要为了减少嵌套把卡片保存与配置保存分成两次提交。补一条大来源准备期间其他读取可完成，以及写入失败后卡片与配置共同回滚的集成检查。

## 3. 对缺失历史原行的工作文字采用显式来源，而非默认公开

**静态代码可确认的退路；尚未证明真实会话触发了泄露。**

`NovexScopedConversationHistory.kt:31` 找不到原消息行时，第 43 行会把没有工具片段的模型消息正文作为公开文字保留。第 34 行也直接保留没有工具和推理字段的用户角色消息。若调用方传入的这些消息是内部生成的摘要、工作文字或工具文本替代物，类型已经被扁平化，投影就无法再辨别它与用户原话／正式回答。

建议为消息投影保留可验证的公开正文来源标记；缺失原行且没有公开标记的内部助手正文按未知来源处理，而不是自动公开。用户明确输入的原话仍应保留，不能一刀切清空历史。增加“原行缺失的执行文字”“文本化内部结果”“明确公开的无原行用户消息”三个边界测试。当前测试主要覆盖原行完整和工具类型完整的情况，不能据此宣称所有缺失来源退路都已隔离。

## 第五项结构整理尚未完成什么

最新盘点：`ChatViewModel.kt`（对话状态管理）约 12,718 行；`NovexWorkspace.kt`（卡片工作空间）约 1,472 行；导入器 283 行、导出器 362 行、共用字段 101 行。卡包迁移减少了工作空间的职责；总控制器仍没有完成迁移，不能以几个新文件宣称第五项完成。

剩余边界明确限定如下：

1. 执行与恢复：`ChatViewModel.kt:7127` 的模型循环、第 8512 行恢复、8543 行权限执行入口、8608 行授权后执行、9982 行消息持久化仍由总控制器协调。应复用已有权限与回合实现，把同一次操作的执行、记录和恢复收进一个模块，不做第二套循环。
2. 资料任务：第 12369 行的通读运行及启动、暂停、恢复入口仍在总控制器。产品核心已经有资料任务规则，下一步只迁出应用调度，不再复制核心规则。
3. 历史与压缩：第 2499 行开始的范围投影接入已分出一部分，但压缩、卸载、历史恢复及实际请求仍依赖总控制器状态。范围策略应在这些入口一致应用，不逐条补临时判断。
4. 页面：对话消息列表、输入区域和弹层宿主仍需按原计划渐进整理；本次未重新展开页面全量审查。
5. 依赖：本次卡包拆分没有新增对界面的反向依赖；导入导出仍依赖原有数据库实体，这是既有技术债。不要在这次有界修复中再复制一整套模型，只在后续真正独立核心类型时处理。

处理顺序：先完成第 1 项回执一致性及对应真实流程回归；第 2 项在内容执行模块进一步收拢时处理；第 3 项补来源边界证明。其余沿第五项既定任务逐步迁移，不扩大成全库重写。
