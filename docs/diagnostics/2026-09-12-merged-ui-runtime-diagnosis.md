## 模块呈现与拖动（B88 及 B101）

1. **拖动横坐标固定，确定。** `novex/android/ModuleTreeEditor.kt` 的手势更新 `point=change.position+origin`，落点同时用 x/y；浮层却是 `IntOffset(0, ...point.y...)`，并固定向上偏移 78.dp。所以落点可正确，浮层只竖向移动，且没有保存抓取位置。此处不是拖动数据保存错误。
2. **预览和编辑用两套目录绘制，确定。** `CardReading.kt` 的递归 `modules` 将所有子模块 `fold=true`，标题只绘制 `Text(module.name, SectionTitle)`；没有编辑页的摘要、文件夹图标、层级缩进。递归展平到同一个 LazyColumn（惰性列表）且没有 depth（深度）参数。父子相同标题看起来同级。
3. **空标题处理不一致，确定。** 编辑模块行和两处横向栏目使用 `ifBlank {"未命名模块"}`，预览纵向标题直接用空字符串，产生只有箭头的行。
4. **摘要直接显示标记语法，确定。** `ModuleExcerpt` 读前 100 字符，只把换行替换成空格，交给普通 Text（文字控件）；所以 `**` 等原始 Markdown（标记文本）会显示出来。展开正文才使用 MarkdownBlock（正文渲染器）。
5. **间距来源，确定到代码参数；实际比例尚未量测。** 预览每个惰性条目额外间距 8.dp，模块标题又使用章节标题与至少 48.dp 的行；编辑页使用普通正文标题、零行间距和分隔线。封面在展示与编辑分别为 1.9 与 1.85 宽高比，且边距不同。简介正文另占惰性条目。截图中简介留白是否还含空正文/换行，缺对应卡包不能确定，不能只归咎于一个固定高度。
6. **同名父子不是错误。** `FolderContents.organize` 按已确认约定将原正文保留为同名子模块、外层容器取得独立编号，保留原正文编号和采用规则；两者能分别重命名。此次应修视觉区分，不应删除这层结构。

## 默认容量、首次闪退、请求失败（B89、B103）

3. **隐藏选料请求的失败通路确定。** `IntegratedCards.candidates` 先调用模型选择模块，随后 `JSONObject(answer).getJSONArray("modules")`，只简单剥离代码围栏。空回复、额外解释或结构不同均直接失败，没有阶段专用错误。该请求使用 `currentProvider.sendMessage`，不通过正文的 `NovexModelStreamRecovery`（流式请求恢复）。故“正文还没开始就报错”并非只有服务不可用一种解释。

5. **首次闪退未定案。** 正常资料准备异常在 `runAgentLoopBody` 中捕获并转为行内错误，不能据“容量不足”推导它必定崩溃。另有已确认的异常边界缺口：发送前 `checkContextBeforeSend` 在外层保护之外；异步发送设置阶段（创建会话、附件准备、保存用户消息、构建基础提示词）外层只有 finally（清理），没有统一捕获。它们是应检查的崩溃通路，但没有现场堆栈，不能选一个冒充本次根因。内存不足/系统终止亦未排除。

### 采用链的实际连接与版本分歧

- `IntegratedCardSettings` 保存 rootId/targetId（根卡/目标编号）到对话的 cardBindingJson（卡片关联记录）；`saveIntegratedCardBinding` 比较旧配置防覆盖并禁止运行中改关联。`IntegratedCards` 通过当前对话配置回读，不是按名称搜索卡片。
- 采用展开世界内部角色后，`RequestMaterials.prepare` 打开指定根卡正式修订，再按目标编号找内容；`ModuleAdoption` 对同编号不同来源/修订显式拒绝，未发现此处随机串卡。
- 最终 `requestSystemPrompt`（请求系统提示词）由采用片段组装，确实传入 `streamMessage`（模型流式请求），不存在“这条线整体没接到请求”的证据。
- **新发现确定的版本分歧：** 自动采用 `store.open` 读取正式版；`CardToolReader.snapshot` 优先 `CardDrafts.read` 读取持久草稿。`IntegratedCards.execute` 将采用对象加入读取权限集合，随后与管理对象共用同一个读取器。因而仅采用的卡片也可能被工具读到未保存草稿，尽管自动注入来自正式版。版本字段有返回，但没有保证两条读取路径使用同一版本。这是代码条件确定的混版通路；是否属于本次错答未定。
- 前述缓存命中缺修订与携带规则仍成立；`saveIntegratedCardBinding` 没有直接清该缓存。管理权限保存本身正确不等于采用快照会更新。不能因发现缓存问题就说所有新请求均有问题。
- `read_card`（读取结构）主要返回名称、模块/资源目录，并没有模块正文；正文由 `read_text_block`（分页读取正文）另取。读取结构成功不能代表正文已经读取。其返回值有内容范围和下一页位置，尚未查到把另一根卡正文任意换入的代码证据。
