# Gemini 中转聊天接口诊断（2026-09-13）

范围：按用户授权读取本机 Gemini 入口，拉取模型并真实请求；不改业务代码、配置或发布。

## 已验证

- 本机登记入口 `https://sub.sailapi.top/v1`，只调用 `/models` 和 `/chat/completions`；钥匙串密钥仅在内存及请求授权头中使用。
- 模型列表 HTTP 200，共 14 个条目；这只是中转站公布的标识，不独立证明背后的真实模型身份或上下文容量。
- `gemini-3.1-pro` 非流式普通聊天返回 OK；流式普通聊天返回完整正文、结束原因和结束标志。`gemini-3-flash-preview` 普通聊天也成功。
- 新版普通聊天参数 `max_completion_tokens` + `stream_options.include_usage=true` 实测成功，不能判定这些字段被一律拒绝。
- 最小 `ping(text)` 工具：非流式成功返回结构化工具调用。流式测试出现过超时、空回复正常结束，也出现成功工具调用。`gemini-3-flash-preview` 的流式工具调用至少一次成功。
- 使用新版参数的三次工具请求：两次 45 秒读取超时，一次 HTTP 200 / 空正文 / 无工具 / stop / completion_tokens=0。原始无凭据请求与响应在 `local/qa/gemini-20260913/results.json`，复测脚本同目录 `probe.py`。
- 再次只切换用量统计选项：关闭时空回复，开启时成功。因此该选项不是确定的单一根因。相同 128 输出额度也既有空回复又有成功，不能断言是额度不足。

## 代码对应

- `ProviderFactory` 根据接口类型选择协议，不根据模型名称自动将聊天补全改为 Gemini 原生协议。选择 OpenAI 接口且不启用 Responses 才是这次用户明确的接法。
- `OpenAIProvider.buildRequestBody` 对该入口发送 `max_completion_tokens`；流式时请求用量统计；工具放在 `tools`，工具选择为自动。
- 流式解析从 `delta.tool_calls` 累积名称和参数。服务端没有返回该字段时，客户端不能凭空恢复真实调用。
- 当前主循环已有空回复最多一次重试，仍失败会显示错误；不是无限工具循环。

## 结论边界

已直接复现中转服务响应不稳定：在完全绕过应用的最小请求里也会空结束或超时。这可解释部分“调用没有结果”，但尚不能证明用户手机的每一次失败都是同一个原因。未获取用户本轮具体失败请求/配置，不能排除手机上选错协议、历史消息、卡片准备等独立问题。

HTTP 200 和 stop 不能当作有可用产出。不能把缺失的工具响应伪造为执行成功。当前证据不足以承诺切换额度字段、关闭用量统计或一律改非流式即可修复全部问题。

## 实际客户端检查

远端已启动 `GeminiOpenAICompatLiveTest`，通过钥匙串密钥经标准输入注入测试进程；结果待完成补记。该测试覆盖真实客户端普通请求和流式工具解析，不包含手机界面与卡片上下文准备。

### 实际客户端结果补记

- 请求实现、接口路由和测试源码三项本机／远端 SHA-256 一致。
- 初次使用默认 2G 编译配置耗时异常，已终止本轮对应进程；按历史成功配置 4G／编译器进程内执行重跑。
- 应用及测试源码均编译通过。真实服务测试运行 35.645 秒，1 项测试、0 跳过、1 断言失败，不是编译错误。
- 测试源码检查先检查普通聊天多数成功，再检查工具多数成功；失败出现在后者，失败明细没有普通聊天失败，因此三轮普通聊天均成功。
- 三轮工具调用均为 `structured=false, finished=true, visible=`：收到终止事件但没有结构化工具调用或可见正文。测试带真实 AgentTools 注册列表，工具输出额度 256。
- 脱敏 XML 在 `local/qa/gemini-20260913/client-test.xml`；远端日志 `gemini-live-20260913-retry.log`。
- 因此新版客户端路径已复现空工具响应现象；直连最小请求也出现同形空响应，确认问题不能仅归因于卡片、历史容量或界面折叠。尚无中转内部日志，不能声称已证明转换丢失、路由分流、某个单一字段等内部根因。
