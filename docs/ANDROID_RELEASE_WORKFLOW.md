# Novex 安卓双通道开发与发布

## 固定分支职责

- `main`：正式分支，只接受已经通过预览候选验证的提交。
- `next`：预览开发分支，日常功能和问题修复的集成位置。
- 任务分支：每项工作从 `next` 创建独立 Git Worktree（Git 工作树），完成后通过 Pull Request（拉取请求）合回 `next`。
- Hotfix（紧急修复）：从 `main` 创建，验证后同时进入 `main` 和 `next`，避免下一条预览线重新引入旧问题。

禁止直接在共享目录中混合多个任务。任务工作树只保存该任务的源代码变化，不保存安装包、截图、构建缓存或临时诊断文件。

## 版本和应用隔离

| 通道 | 应用标识 | 版本示例 | 更新范围 |
|---|---|---|---|
| 正式版 | `com.noven.player` | `0.2.4` | 只接收非预发布的正式版本 |
| 预览版 | `com.noven.player.preview` | `0.2.4-beta.12`、`0.2.4-rc.15` | 接收预览候选版本 |

`next` 中 `app/build.gradle.kts` 的默认版本代表“下一次准备发布的正式版本”。预览流水线只在构建时追加 `beta`（测试版）或 `rc`（候选版）标识，不修改源代码中的正式目标版本。

候选包不得使用没有后缀的正式版本号。正式版本发布后，晋升流水线自动把 `next` 的默认版本推进到下一个修订版本，并使用 `[skip ci]`（跳过持续集成）避免仅版本号变化触发一次无意义的候选构建。

## 发布路径

### 1. Android quick validation（安卓快速验证）

文件：`.github/workflows/android-validate.yml`

- 在面向 `main` 或 `next` 的 Pull Request（拉取请求）上运行。
- 执行稳定通道单元测试和预览通道 Kotlin（科特林）编译。
- 新提交会取消同一拉取请求中尚未完成的旧验证。
- 文档之外没有相关代码变化时不运行。

这条流水线负责尽早发现问题，不生成正式安装包。

### 2. Windows fast preview publish（视窗系统快速预览发布）

入口：`scripts/publish_android_preview_fast_windows.sh`

- `--dry-run` 只显示下一版本与固定发布目标，不构建、不上传。
- 不带发布参数时，在常驻 Windows（视窗系统）构建目录中执行增量验证、构建不执行 R8（安卓代码压缩优化器）的非调试签名包，并把校验后的候选复制到 `tmp/novex-fast-publish/`。
- `--publish` 只允许从干净、已推送且无分歧的 `next` 发布；它固定校验 `com.noven.player.preview`、预览版本后缀、签名证书和 SHA-256（安全哈希算法）。
- 上传先进入不可见草稿；安装包、内部更新文件和校验清单核对一致后，才把草稿转为公开预发布版本。
- Windows（视窗系统）镜像每次都按实际文件哈希与本地比较。失败构建遗留的源码不能再被误当成已同步状态。

这是日常测试版，只用于立即更新查看。它不会生成正式版、不会修改 `main`，也不能直接作为正式版晋升候选。

### 3. Android preview candidate（安卓预览候选云端备用路径）

文件：`.github/workflows/android-preview.yml`

- 只在 GitHub Actions（GitHub 自动化流水线）中手动运行。选择预览包时可作为 Windows（视窗系统）不可用的备用路径；选择正式候选时执行完整测试、R8（安卓代码压缩优化器）和签名校验，供后续正式晋升使用。
- 对该源代码 SHA（提交哈希）执行一次完整单元测试。
- 构建并公开发布独立预览安装包。
- 不会因为普通 `next` 推送自动重复打包。

完整测试、R8（安卓代码压缩优化器）、签名和耗时编译都在这条备用路径中完成。

### 4. Android promote stable（安卓正式晋升）

文件：`.github/workflows/android-promote.yml`

- 仅允许手动执行；默认是安全演练，只下载并验证候选，不改动分支、标签或正式发布。
- 默认选择最近一次成功的 `next` 候选运行，也可以输入指定运行编号。
- 检查候选运行确实成功、来源是 `next`、提交可以从 `main` 快进、候选仍属于当前 `next` 历史。
- 重新核验安装包哈希、应用标识、正式版本、签名证书和标签，但不重新编译。
- 将经过验证的来源提交快进到 `main`，创建正式标签并发布原始候选安装包。

候选生成后如果只增加了流水线或文档变化，晋升会比较 `src/android`、安卓依赖、沙箱准备脚本和子模块配置。只有这些产品输入完全一致时，才允许将包含管理改动的最新 `next` 提交作为正式标签目标；任何安卓产品输入变化都会拒绝晋升并要求生成新候选。

需要真正发布时必须显式打开 `publish`（发布）选项。建议先保持关闭运行一次，确认页面摘要中的提交、版本和验证结果，再打开后执行正式晋升。

正式晋升使用预览阶段已经构建的同一份字节产物，不允许“内测一份、发布时重新构建另一份”。

## 日常流程

1. 在独立任务工作树中开发并运行针对性测试。
2. 提交面向 `next` 的拉取请求，由快速验证流水线检查。
3. 合入并推送 `next`，先运行快速发布命令生成本地候选；确认元数据后使用 `--publish` 发布同一来源的新预览版本。
4. 内测人员直接通过预览应用更新并验证。
5. 有问题则继续任务工作树 → 拉取请求 → 新候选版；不要修改旧候选产物。
6. 需要形成可晋升的正式候选时，单独运行云端完整候选流程，再由“Android promote stable”执行正式晋升。
7. 正式发布完成后，流水线自动开启下一条预览版本线。

## 发布说明

优先在 `.github/release-notes/v版本号.md` 编写简短中文更新内容。同一文件同时供预览候选和正式版使用。

如果尚未提供该文件，`scripts/render_android_release_notes.sh` 会根据上一个正式标签后的提交自动生成基础列表，保证预览和正式更新界面不会再次出现空白或原始比较链接。

## 故障处理

- 正式版崩溃、无法启动、数据损坏或无法更新：从 `main` 建立紧急修复，完成快速验证后生成一个专用候选，再执行正式晋升。
- 普通高优先级问题：进入最近一次 `next` 候选，不直接污染 `main`。
- 构建失败：修复原提交并生成新候选；不得手工替换已经验证过的候选产物。
- 候选产物超过 30 天：重新运行预览候选流水线，获得新的完整验证和签名产物后再晋升。
